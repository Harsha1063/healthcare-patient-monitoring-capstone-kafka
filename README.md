# Healthcare Patient Vital Monitoring & Real-Time Alerting System

## 1. Project Overview

The **Healthcare Patient Vital Monitoring & Real-Time Alerting System** is a data engineering capstone project designed to process patient vital-sign events generated by medical devices and identify abnormal health conditions.

The system demonstrates an end-to-end data pipeline using:

- **Scala** for event generation
- **Apache Kafka** for event ingestion
- **Apache Spark 3.5.6** for data processing and rule-based alert detection
- **CSV** for the processed output
- **Apache Hive** for analytical table schema design
- **Apache HBase** for NoSQL storage schema design
- **SBT** for Scala project build and execution
- **Git/GitHub** for version control

### Important implementation note

The current verified implementation uses **Kafka batch consumption through Spark**. It is not a continuously running Spark Structured Streaming application.

The project demonstrates the streaming architecture concept and Kafka-based event ingestion, while the current Spark implementation reads the available Kafka records in a batch, processes them, and generates the CSV output.

Hive and HBase are currently represented through their **schema definitions** in the project. They are not configured as live sinks in the current verified implementation.

---

# 2. Problem Statement

Healthcare devices continuously generate patient vital information such as:

- Heart rate
- Body temperature
- Blood oxygen level
- Patient ID
- Device ID
- Timestamp

Manually monitoring these values can make it difficult to identify abnormal conditions quickly.

The objective of this project is to build a data pipeline that:

1. Receives patient vital events through Kafka.
2. Parses the event data using Spark.
3. Removes duplicate events using `event_id`.
4. Applies predefined healthcare rules.
5. Classifies each patient event as:
   - NORMAL
   - ALERT
   - CRITICAL
6. Stores the processed result as a CSV output.
7. Provides Hive and HBase schemas for future analytical and NoSQL storage.

# 10. Patient Event Format

Patient events are represented as JSON messages.

Example:

```json
{
  "event_id": "EVT200001",
  "patient_id": "P100",
  "device_id": "DEV001",
  "heart_rate": 78,
  "temperature": 36.8,
  "oxygen": 98,
  "timestamp": "2026-09-23 17:15:00"
}
```

### Fields

| Field | Description |
|---|---|
| event_id | Unique identifier for the patient event |
| patient_id | Patient identifier |
| device_id | Medical device identifier |
| heart_rate | Patient heart rate |
| temperature | Patient body temperature |
| oxygen | Blood oxygen level |
| timestamp | Event timestamp |

# 13. Alert Classification

The rules are combined to classify each event.

### NORMAL

No abnormal condition is detected.

Example:

```text
Heart rate: 78
Temperature: 36.8
Oxygen: 98

Status: NORMAL
```

### ALERT

One abnormal condition is detected.

Example:

```text
Heart rate: 145
Temperature: 37.1
Oxygen: 97

Status: ALERT: HIGH_HEART_RATE
```

### CRITICAL

Multiple abnormal conditions are detected.

Example:

```text
Heart rate: 145
Temperature: 39.2
Oxygen: 88

Status:
CRITICAL: HIGH_HEART_RATE, LOW_OXYGEN, HIGH_TEMPERATURE
```

A simple explanation can be:

> "This project demonstrates a healthcare data engineering pipeline. I generate patient vital events using a Scala Kafka producer and publish them to a Kafka topic called `patient-vitals`. Spark then reads the available Kafka records, parses the JSON data, removes duplicate events based on `event_id`, and applies healthcare rules for heart rate, temperature, and oxygen levels. # 31. Important Architecture Clarification

The project architecture is designed around real-time healthcare event processing, but the current verified implementation should be described accurately as:

```text
Kafka-based event ingestion
+
Spark batch processing of available Kafka records
+
Rule-based healthcare classification
+
CSV output
```

It should **not** be presented as a continuously running Spark Structured Streaming job in the current implementation.

Similarly:

```text
Hive schema → designed, not a live sink
HBase schema → designed, not a live sink
CSV → verified live output
```

This distinction makes the project explanation technically accurate and clear.
